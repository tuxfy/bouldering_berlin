# Stufe 6: QA

Prüft eine umgesetzte Anforderung über die Tests hinaus, bevor der Nutzer sie abnimmt. Voraussetzung: Stufe 5 abgeschlossen, alle Tests und Prüflauf grün, Status `qa`, Arbeit auf dem Feature-Branch.

| Schritt | Wer | Ergebnis |
|---|---|---|
| 6a Automatische Prüfungen | Agent | Ergebnis unter `# QA → Automatisch` |
| 6b Prüfung durch Rollen | Prüfer (nur lesend) | Befunde nach Gewicht |
| 6c Befunde bearbeiten | Agent | blockierende behoben, Rest entschieden |
| 6d CI | Agent | Pull Request eröffnet, CI grün |
| 6e Abnahmepaket | Agent | Paket für den Nutzer, Status `review` |

## Umfang

| Art der Änderung | 6a | Reviewer | Klicktester | Security |
|---|---|---|---|---|
| Bug (`_anweisungen/01-idee.md`, Weg eines Bugs) | ✓ | ✓ | ✓ bei UI | bei Bedarf |
| Kleiner Fix ohne UI | ✓ | — | — | — |
| Feature oder größere Änderung | ✓ | ✓ | ✓ bei UI | bei Bedarf |
| Neue Abhängigkeiten, gespeicherte Daten, externe Dienste, Auslieferung | ✓ | ✓ | ✓ bei UI | ✓ |

Rollen und Prüfpunkte: `_anweisungen/rollen/`. Unabhängige Prüfer mit frischem Blick, die nur lesen (in Claude Code als Unteragenten unter `.claude/agents/`; sonst eigene Sitzung je Rolle).

## 6a: Automatische Prüfungen

-   Alle Prüfungen aus `_kontext/projekt.md` → „Prüfungen" (in Stufe 0 festgelegt).
-   Was dort festgelegt, aber (noch) nicht eingerichtet ist oder nicht lief: im QA-Abschnitt ausdrücklich nennen, nicht still weglassen.
-   **Warnungen, die nicht blockieren** (z. B. Schwachstellen in Entwicklungswerkzeugen): als Hinweis unter `# QA`; ist eine neu und nicht schon als Idee erfasst, Idee im Backlog anlegen (z. B. `werkzeuge-aktualisieren`).
-   Ergebnis unter `# QA → Automatisch`: je Prüfung Befehl und Ergebnis.

## 6b: Prüfung durch Rollen

Die Rollen laufen **parallel** (siehe `_anweisungen/rollen/README.md`); der Agent führt die Ergebnisse zusammen und fasst doppelte Befunde zusammen.

-   **Reviewer:** liest den Diff des Feature-Branches gegen Anforderung, Plan und Entscheidungen.
-   **Klicktester:** bedient die laufende App im Zielformat aus dem Projektkontext, entlang des „Verhaltens" der Anforderung und erkundend darüber hinaus; Screenshots der wichtigen Zustände unter `.qa/` (nicht committet), neben dem Entwurf.
-   **Security:** prüft nach Checkliste; Befunde nur abstrakt festhalten.

## 6c: Befunde bearbeiten

-   **Blockierend:** zurück zu Stufe 5 (5c/5d) — mit Test, wo möglich; danach QA erneut, mindestens die betroffenen Prüfungen.
-   **Empfohlen:** umsetzen oder mit Grund ablehnen; was später kommen soll, als Idee ins Backlog.
-   **Hinweis:** nach Ermessen; nichts muss.
-   **Ändert der Agent in der QA etwas:** wie in Stufe 5 — Test, wo möglich (erst rot, dann grün), danach alle Prüfungen erneut; Eintrag im Testnachweis. Unter `# QA → Befunde` steht **je Änderung** der Test (Name) oder, warum es keinen gibt — ohne eins von beiden gilt die Änderung als nicht abgeschlossen. Jede Korrektur ist ein eigener Commit.
-   Berührt ein Befund eine Entscheidung der Anforderung: nicht selbst entscheiden — dem Nutzer vorlegen.
-   Ergebnis unter `# QA → Befunde`: je Befund kurz, was damit passiert ist.

## 6d: CI

-   Nach den Befunden: sauberer Lauf grün, dann den Branch pushen und einen **Pull Request in den Release-Kandidaten** `rc/<version>` eröffnen; der CI-Lauf läuft dort.
    -   Gibt es noch keinen offenen Release-Kandidaten: Der Nutzer legt die Version fest; der Agent legt `rc/<version>` von `main` an, darauf `releases/<version>.md` nach `_anweisungen/vorlagen/release.md`, und pusht ihn.
    -   Bei der Abkürzung (`08-release.md`): Pull Request direkt nach `main`.
-   **CI-Lauf abwarten** (im Pull Request).
-   **Rot in der CI:** zurück zu Stufe 5 — zuerst klären, warum lokal grün war (was hat lokal anders gelegen?), und das als Test bzw. im sauberen Lauf absichern.
-   Ergebnis unter `# QA → CI`: Lauf grün (Commit).

## 6e: Abnahmepaket

Für den Nutzer, kurz und in Alltagssprache, im Gespräch:

-   **Was umgesetzt ist** — drei bis fünf Sätze.
-   **Screenshots** der wichtigen Zustände aus `.qa/`, neben dem Entwurf (bei UI).
-   **Was die QA gefunden hat** und was damit passiert ist.
-   **Was die automatische Prüfung nicht abdecken konnte** — ausdrücklich, damit der Nutzer gezielt danach schaut (z. B. andere Browser-Engine als auf dem Zielgerät, Installation, Funktionen, die nur am echten Gerät laufen).
-   **Checkliste für die Abnahme** — die Kriterien mit Prüfung „manuell", als konkrete Handgriffe (z. B. „am iPhone: Kopieren, in Notizen einfügen, Text vergleichen").
-   **Wie die Abnahme lokal startet** (Befehl aus `_kontext/projekt.md`).

Status `review`; weiter mit `_anweisungen/07-abnahme.md`.
